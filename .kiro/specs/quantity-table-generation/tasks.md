## Implementation Notes

- 55.1 (REQ-39 根本原因): 写真一覧は `QuantityTableEditPage.tsx` 内インライン実装（`styles.photoGrid`/`styles.photoItem`、`availablePhotos.map`）。`photoGrid` は `display:grid` + `gridTemplateColumns: repeat(auto-fill, minmax(150px,1fr))` + `flex:1` + `overflowY:auto` だが `gridAutoRows` 未指定（既定 `auto`）。各セル高さは `photoItem` の `aspectRatio:'1'` のみに依存。flex(`flex:1`)+overflow 制約下で implicit grid row が aspect-ratio から高さを確定できず、複数行折り返し時に行が潰れて写真が重なる。修正方針: `photoGrid` に `gridAutoRows`（列幅に追従する固定高）を明示し、`photoItem` に `minHeight` フォールバックを併用。重なりゼロの矩形判定は jsdom 不可のため E2E（getBoundingClientRect）で検証する。写真取得方式・注釈バッジ（REQ-3.3）は不変。選択・変更とも同一 `handleSelectImage` 経由のため当該1箇所の修正で両対応。
- 55.3 (REQ-39 E2Eが実バグ検出): `gridAutoRows:'150px'` のみでは重なりが残った。`gridTemplateColumns: minmax(150px,1fr)` で列幅が150px超に伸びると `photoItem` の `aspectRatio:'1'` 由来の高さ(=列幅)が固定行トラック150pxを超過し次行へ食い込み重なる。`photoItem` を `aspectRatio:'1'`→`height:'150px'`（definite height、minHeight:'150px'維持）に是正して解消。img は `objectFit:'cover'` 維持のため視認性不変。重なりゼロは E2E（getBoundingClientRect 全ペア判定）でのみ検証可能。
- E2E環境の注意: frontend テストコンテナは nginx 静的ビルド（5174→80、ソース未マウント）。フロントの CSS/コード変更を E2E に反映するには `npm run test:docker:build`（frontend `--build`）でのリビルドが必須。
- 59.4 (REQ-42 saveDraft 並行制御の実態): saveDraft は design.md L2073 のとおり `expectedUpdatedAt` 楽観ロックのみ（FOR UPDATE 行ロックは任意・不採用）。検証の結果、真の同時並行 save（Promise.all）は READ COMMITTED 下で非決定的（両 tx が読取段階を通過し、後発が削除済み行の更新/削除に当たり 500 になり得る）であり、design L2073 が述べる「並行 save は後発が 409」は厳密には stale-token（逐次）競合でのみ決定的に成立する。統合テストは design 準拠で stale-token 逐次競合（後発409・部分反映なし・displayOrder 衝突なし）を決定的に検証する方針に統一した。真の同時並行での 409 保証が必要なら saveDraft への FOR UPDATE 行ロック導入が別途必要（Note 56.5 と同系の並行制御課題）。なお中断した初回実装が service へ FOR UPDATE を追加して単体テストを破壊したため、承認済み設計（楽観ロック主）に従い service を HEAD へ復元した。
- 56.5 (REQ-40 並行制御ギャップ・要エスカレーション): from-survey 自体は設計どおり `quantity_tables` 行へ `SELECT FOR UPDATE` を取得し直列化する（copy も同様）。ただし design.md L1816 が主張する「add/copy/reorder/from-survey の4種完全直列化」は現状の実装では未達。`create`(add) と `updateDisplayOrder`(reorder) はロック非取得＋呼び出し側 displayOrder リテラルをそのまま書き込み、`(quantityTableId, displayOrder)` のDB一意制約も無いため、4種混在の並行実行では displayOrder 衝突・欠番が起こり得る。これは REQ-40 が作り込んだ不具合ではなく、add/reorder に元から存在する並行制御の限界。56.5（テスト専用・実装変更禁止）はロックが実際に保証する from-survey×2 + copy に並行テストを限定し衝突/欠番ゼロを検証、ギャップを開示した。**上位対応の選択肢**: (1) design L1816 の記述を実態（copy/from-survey のみ直列化）に合わせて修正する / (2) create()・updateDisplayOrder() にも `quantity_tables` 行ロックを導入し、併せて displayOrder のDB一意制約追加を検討して4種完全直列化を実装する。並行制御の設計/実装課題として別途判断が必要。

- 65.1 (後続タスクへの申し送り): (a) 計算式文字列の書式は `generatePitchFormula()` に合わせ `toFixed` を使わない素の値（`5 x 2.5 x 1.5 = 18.75`）。design.md の例示が小数2桁になっていた誤りを訂正済み。小数2桁は入力フィールドの表示整形（68.2）の話で計算式文字列とは別物。 (b) `calculateCount()` は箇所数が未入力・整数以外・範囲外だと**例外を投げる**（既存の `calculatePitch()` と同じ流儀）。68.3 の UI 結線では、既存の面積・体積／ピッチと同様に **`calculate()` 呼び出しを try/catch でガードし、例外時は数量を更新しない**こと。 (c) `calculation-engine.ts` に `COUNT_MIN`(1) / `COUNT_MAX`(9999999) を定義済み。66.1 の整数範囲バリデーションはこれを参照し、範囲の二重定義を避けること。
- 66.2 (後続タスクへの申し送り): (a) `quantity-validation.service.ts` の `CalculationMethodType` は独自リテラル union をやめ、`quantity-table.schema.ts` の `CALCULATION_METHODS` から `import type` で派生させた（循環 import なし。schema 側は zod のみに依存）。**計算方法の列挙を新たに書き足す場面では、必ず `CALCULATION_METHODS` を単一情報源として参照すること**（67.2 のルート側ハードコード解消も同じ方針）。 (b) `validateQuantityItem` の switch に `default` 節を追加し、未知の計算方法を `field: 'calculationMethod'` の検証エラーにした（従来は無検証で `isValid: true` を返していた）。 (c) COUNT モードでは `length` / `weight` を検証しない。これは既存 `validatePitchMode` が任意項目を検証していないのと同一の流儀で、REQ-47 の「ピッチと同一挙動」と整合する。
- 67.1 (後続タスクへの申し送り・重要): (a) 旧 `calculationParamsSchema`（形状推測の `z.union`）は**削除済み**。計算パラメータの検証は `PARAMS_SCHEMA_BY_METHOD`（`Record<CalculationMethodType, z.ZodType>`）＋ `withCalculationParams()` に一本化した。新規に計算パラメータを検証する箇所を書く場合は必ずこれを使うこと。 (b) `withCalculationParams()` は `superRefine` 内で出力オブジェクトの `calculationParams` を破棄後の値に差し替える。zod v4 の ZodObject が入力とは別の出力オブジェクトを生成するため `req.body` は汚染されない（レビューで実測確認済み）。 (c) **地雷**: refinement を持つスキーマに `.omit()` / `.partial()` を掛けると zod v4 は実行時例外を投げる。派生が必要な場合は素の `createQuantityItemBaseSchema` / `updateQuantityItemBaseSchema` から派生させ、最後に `withCalculationParams()` を再付与すること（`.extend()` は refinement を保持するので可）。 (d) 検証層の前倒しにより、必須パラメータ欠落は service 層ではなく zod 段階で 400 になる。セル単位エラー表示（REQ-11.4 / 42.9）の文言が英文へ劣化しないよう、ピッチの必須4キーにも `QuantityValidationService.validatePitchMode` と同一の日本語メッセージを付与済み。**計算パラメータのスキーマに必須項目を足す際は日本語メッセージを必ず添えること**。 (e) 一括保存の `saveDraftItemSchema` の計算方法 enum は `['STANDARD','AREA_VOLUME','PITCH']` のままで COUNT は 400 になる。**67.2 で解消すること**。
- 68.1 (後続タスクへの申し送り): (a) `CalculationFields.tsx` に `FIELDS_BY_METHOD: Record<Exclude<CalculationMethod,'STANDARD'>, FieldDefinition[]>` を新設・export した。`STANDARD` を除外できるのは本体冒頭の `if (method === 'STANDARD') return ...` 早期リターンで型が絞り込まれるため（危険なキャストは不使用）。**この早期リターンを外すとコンパイルエラーになる（fail-loud）**。 (b) `FieldDefinition` に `integer?: boolean` を追加し `COUNT_FIELDS.count` に付与済み。ただし**メタ情報を持たせただけで `NumberInputField` へは渡していない**。整数の表示整形・入力制御は 68.2 の担当（現状 COUNT の箇所数は「5.00」と表示される）。 (c) `FIELDS_BY_METHOD` と `calculation-method.ts` の `PARAM_KEYS_BY_METHOD` はキーが二重管理になるが、**片方だけ変更すると落ちる整合性テスト**で束縛済み。どちらかを変更する場合は必ず両方を揃えること。
- 68.2 (後続タスクへの申し送り): (a) 3経路の書式分岐は `formatFieldValue(value, integer)` の1関数に集約した（`useState` 初期値 / props 同期 / blur）。**新たに整形経路を足す場合は必ずこの関数を経由させること**。分岐が散ると「blur だけ整数化して props 同期で 5.00 に戻る」不整合が再発する。 (b) 整数・範囲の判定は 66.1 の `validateNumericRange(value, 'count')` に**完全委譲**した。`CalculationFields.tsx` 側にリテラル（`Number.isInteger` / `1` / `9999999`）を直書きしないこと。 (c) **REQ-47 AC10/AC11 の「拒否」を、blur 時に onChange を呼ばない実装で表現した**。結果として、不正値を入れて blur するとエラー表示のまま入力欄には不正テキストが残り、親の `calculationParams` は直前の正当値を保持する。**68.6（保存前整合性チェック）で「エラー表示中の保存」の扱いを検討すること**（画面のテキストと保存値が一時的に食い違う）。既存 `AdjustmentField` は「既定値へ強制＋警告」で流儀が異なるが、これは AdjustmentField に拒否要件が無いための差。
- 68.3 (調査結果・後続タスクへの申し送り): **`EditableQuantityItemRow.tsx` は最初から COUNT を取りこぼしていなかった**。4つの再計算ハンドラはいずれも計算方法を列挙せず `!== 'STANDARD'` で分岐し、`calculate()` に `calculationParams` を丸ごと渡すため、`case 'COUNT'`（65.1）があれば `count` は素通しで届く。調整係数・丸めも同じ共通後段を通るのでピッチと同一の挙動が構造的に保証される（レビューで grep 実測確認）。無言のフォールバックは `CalculationMethodSelect.tsx:45-49` の配列リテラルのみで、実コード変更もそこだけ。**この「計算方法を列挙しない」構造を壊さないこと**（列挙を書いた瞬間に第5の計算方法で同じ不具合が再発する）。
- 68.4 (**71.4 の E2E 設計に直結する重要な知見**): (a) **パラメータ残留バグは DOM に一切現れない**。`CalculationFields` は `FIELDS_BY_METHOD[method]` に定義されたフィールドしか描画しないため、切替後に残留した旧方式のキーは構造的に画面へ出ない。**画面表示だけを見る E2E は REQ-48 に対して常に緑になる偽の緑**。71.4 は必ず「保存 → リロード → 復元値」で確認するか、`POST .../save` のリクエストボディ（`calculationParams`）を network intercept で検証すること（レビューで実測確認: pre-68.4 コードでも DOM アサーションは全通過し、`onUpdate` ペイロード検証でのみ失敗した）。 (b) **切替直後の数量は「据え置き」とは限らない**。design は「切替後は必須パラメータ未入力で `calculate()` が例外を投げるため数量は更新されない」と書いているが、これは**面積・体積では成立しない**（`calculateAreaVolume` は全項目未入力でも例外を投げず 0 を返す。共通フィールドの重量だけが引き継がれた場合は重量のみで再計算される）。71.4 の AC7 検証を「数量が据え置き」と書くと面積・体積で必ず落ちる。**「旧方式に固有のパラメータ由来の値でないこと」**を主張する形で設計すること。
- 68.6 (**design の誤認を発見 → 68.7 を新設**): `useQuantityTableSave` フックは **production から import 元がゼロのデッドコード**（`useMemoizedCalculation` と同類）。design.md の File Structure Plan がこのフックを保存経路だと誤認していた。実際の保存は `QuantityTableEditPage.handleSave`（:1374）で、独自のインライン検証（項目名・丸め設定のみ）を行い、409 以外のエラーを `保存に失敗しました。再度お試しください。` に潰している（:1430。バックエンドの「箇所数は必須です」は `ApiError.response` に入っているが読んでいない）。結果 **REQ-47 AC9 を満たす経路が製品内に存在しない**（既存のピッチ REQ-8 AC10 も同じ穴）。68.6 のコード自体は design 準拠・テスト十分・境界遵守のため維持し、**配線を 68.7 として新設**した（ユーザー判断: 保存前チェックを画面へ配線）。**今後 `useQuantityTableSave` に何かを実装しても製品には届かない。保存の振る舞いを変えるなら `QuantityTableEditPage.handleSave` を触ること。**
- 71.1 (**クリップ検出の要点**・後続 E2E への申し送り): (a) **`toBeVisible()` も `boundingBox()` もクリップを検出しない**（実装者・レビュアーの双方がプローブで実測。旧実装で `toBeVisible()` は全通過する）。検出の本体は **`document.elementFromPoint` によるヒットテスト**（各メニュー項目の矩形上3点で最前面要素が当該項目かを判定）。クリップされた領域はヒットテストの対象外になり祖先の `<div>` が返る。 (b) 併せて「メニューがクリップ元ラッパーの下端を**超えている**こと」を**必須の前提アサーション**として置くこと。これが無いと「そもそもはみ出していないので検証が空虚」になる。 (c) E2E のフロントは nginx 静的ビルドなので、**フロントを変更したら `npm run test:docker:build` でのリビルドが必須**。 (d) メニューはフリップ（上開き）しない設計（要件・設計とも要求していない）。ビューポート下端付近の行ではメニューが画面外に出るため、テストは対象行を `scrollIntoView({block:'center'})` で中央へ寄せてから開くこと。

## Implementation Notes（越境して実行された是正）

- **変換中の記録の寿命は「揃えるのは寿命、終端の置き場所は構造に従う」**: 補完候補の入力欄と数量項目の入力欄は焦点を得た時点で初期化し、数量グループ名は焦点を失った時点で消す。グループ名の編集欄は空欄では確定できず焦点喪失後も残るため編集開始側では覆えず、補完候補の入力欄は候補一覧へ焦点が移ると焦点喪失の処理が早期に戻るため焦点喪失側では覆えない。**見た目の対称性を求めて三箇所の機構を揃えると穴が開く。**
- **入力の拒否は変換中を必ず考慮すること**: 単位欄で「立米」が「りゅう」になる類の破壊は、E2E の入力補助でも単体の変更イベントでも変換を経由しないため構造的に検出できない。変換中の扱いは実装とコードの読みで担保すること。
- **保存要求の重複検出はグループと項目で集合を分ける**: 別の表の識別子であり、同じ値であっても重複ではない。集合を統合すると正当な要求を誤って拒否する。統合すると失敗する検証が入っている。
- **補完候補の上限は取得の時点で濾す**: 選択の経路が二つ（クリックと矢印＋確定）あり、いずれも同一の候補配列を参照するため、取得時点が単一の関門になる。

- **範囲判定と既定値差し替えは層であり、順序を条文で決めないと結線が二通りになる**: 80.1 は「既定値へ差し替えてから範囲判定へ渡す」（REQ-10.4 優先）で決着させ、条文・正典の doc・design.md・単体検証の4箇所へ書いた。逆順に結線すると `e2e/specs/quantity-tables/field-specification.spec.ts` の `10.4: 丸め設定が0の時は0.01が自動設定される`（現在緑）が落ちる。**描画される実装は既にこの順序で動いている**——`CalculationFields.tsx` の `AdjustmentField.handleBlur` が `numValue === 0 && defaultValue !== 0` で差し替える（丸め設定は `defaultValue={0.01}`）。
- **範囲を課す層は焦点喪失だけではない**: `frontend/src/pages/QuantityTableEditPage.tsx` の `handleSave` が `Number(item.roundingUnit) <= 0` を「丸め設定が無効です」として保存を中断する（REQ-11.2 の整合性チェック）。この層は `0` を差し替えず拒否するため、AC 4 の全称的な順序規定と向きが逆である。UI からこの枝へ `0` が届く経路は現状見当たらないが、**「結線先は一つ」と決めてかからないこと。**
- **同一部品の既定値差し替えが、条文の裏づけの無い欄へ相乗りしていることがある**: `AdjustmentField` の `0 → 既定値` 差し替えは調整係数（`defaultValue={1.0}`）にも掛かるが、REQ-9.4 が既定値差し替えの対象と定めるのは**空白のみ**であり、`0` は REQ-9.3 の有効域 `-9.99〜9.99` の内側である。実装のコメント自身が「0の場合もデフォルト値を設定（丸め設定用）」と書いており意図せぬ波及である。**「AC 4 が先」を他の欄へ横展開しないこと。**
- **正典を一本化するときは、撤去する輸出の消費者を HEAD で全数列挙すること**: 80.1 は `field-validation.ts` から `validateNumericRange` / `NUMERIC_FIELD_RANGES` を撤去したが、消費者を数え上げていなければ「黙って検証を失った呼び出し側」を見落としうる。実測では本番の消費者は `FieldValidatedItemRow.tsx` の1ファイルのみだった。**撤去後に全件が緑であることは、検証が消えたことを検出しない。**
- **既定値差し替えを断つと、それまで到達不能だった「保存だけが落ちる」領域が開く**: 80.2 が調整係数の `0 → 1.00` 相乗り差し替えを条文どおり断った結果、`0` がそのまま確定し数量が `0` になり、`backend/src/routes/quantity-tables.routes.ts` の `adjustmentFactor: z.number().positive()` が保存だけを 400 で拒む経路が開いた。**差し替えは条文違反であると同時に、条文と実装の食い違いを覆い隠す蓋でもあった。** 蓋を外すときは、覆われていたものを同時に数えること。
- **同じバックエンドの中で条文どおりの制約と食い違う制約が併存しうる**: 調整係数は `quantity-field-validation.service.ts` の `FIELD_CONSTRAINTS.ADJUSTMENT_FACTOR` が条文どおり `-9.99〜9.99` で、しかも `validateItemFieldSpecs` → `validateDraft` → `saveDraft` の経路で**生きている**。実際に `0` を弾いているのはルート層の zod が先に走るためである。**「バックエンドがこう定めている」を一箇所だけ見て決めないこと**——どちらが少数派かで、条文を狭めるか実装を直すかの向きが変わる。
- **変異の当て損ないは結線の穴と区別がつかない**: 80.2 の初稿は寸法12欄の `rangeFieldType` を文字列置換で一括除去しようとしたが、整形の都合で `pitchLength` の1件だけ字面が一致せず残り、報告では「ピッチ長は取りこぼした」と書かれた。独立レビューがピッチ長**単独**の変異を当てて 2 failed / 118 を実測し、結線も検出も生きていることが分かった。**一括変異で落ちなかった箇所は、個別に当て直すまで結論を出さないこと。**
- **12箇所の結線に対し検証が11箇所でも、一括変異では気づけない**: ピッチモードの「重量」だけ検証が無い状態で、12箇所すべてを外す変異は 23 件落ちた。落ちた件数が十分に大きいと穴は隠れる。**欄ごとに1件ずつ変異を当てるか、結線の数と検証ケースの数を突き合わせること。**
- **範囲外を拒むときの見え方が欄ごとに揃っていない**: 数量欄と調整係数・丸め設定は小数2桁へ整形してから拒み（REQ-14.2 の常時2桁表示に合わせる）、寸法・ピッチ・箇所数の各欄は生入力を保ったまま拒む（箇所数で Task 68.2 が定めた作法）。**この非対称が、ラチェット `quantity-table-crud.spec.ts:4003` / `:4106` が `test.fail()` を外すだけでは緑にならない直接の原因である。** 揃えない判断と材料は design.md に記録した。
- **結線すると壊れる検証だけでなく、結線しても壊れない「偽の緑」を数えること**: `e2e/specs/quantity-tables/field-specification.spec.ts:600-628` は撤廃済みの範囲 `-99.99〜99.99` を主張し続けるが、拒否時にも整形値が欄へ残るため**緑のまま通る**。80.2 の初稿は「壊れる」と誤って分類し、独立レビューが実読で覆した。**「壊れないから引き継ぎ一覧から落とす」は、次の担当者に見落とさせる。**
