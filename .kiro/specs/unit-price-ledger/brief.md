# Brief: unit-price-ledger（単価台帳）

## Problem

見積担当者が実行金額を組むとき、協力会社から過去に取った見積の単価を参考にしたい。現在、その過去の見積は ArchiTrack の外（Google ドライブ上の「単価台帳」。1 見積 1 ファイルの JSON の見積カードと、登録のたびに作り直す Excel の一覧）にある。ローカルの Claude と共通スクリプト（daicho）だけが扱えるため、次の問題がある。

- 見積作成の画面からは過去の単価が見えない
- ほかの利用者が使えない
- ArchiTrack の受領見積と台帳に同じ見積が二重に登録される

## Current State

- ArchiTrack の受領見積（estimate-request 要件11・14）は、明細行（名称・規格・単位・数量・単価・金額・備考、任意分類・工種）を構造化して持ち、見積カードとほぼ同じ形をしている。ただし次の制約がある
  - 受領見積は必ず見積依頼に紐付く（14.1。モデルの estimateRequestId が必須）
  - 業者名は受領見積自体に持たず、見積依頼の取引先から引いている
  - 見積カードが持つ次の項目が無い：行の区分（諸経費・交通費・産廃・値引き・法定福利費・別途）、条件、換算、案件の条件（場所・改修／新営・用途・工事価格・作業条件・距離）、参考の印、読取の確認、採否・確定金額
- 案件をまたいで過去の単価を探す仕組みは、どの spec にも無い
- 見積カードの形は共通スクリプトの daicho の先頭の説明が定める。カードは Google ドライブの台帳の cards フォルダにある。この環境からは件数が見えず、件数は未確認

## Desired Outcome

- 保管しているすべての見積カードが、文字情報として ArchiTrack の台帳に入っている。原本の PDF は持たず、カードの原本のパス（Drive 上の場所）を文字で残す
- 今後、受領見積を登録すると、それがそのまま台帳に載る（二重登録が無い）
- システム管理者が台帳全体を一覧・検索・修正でき、「要確認」（参考の印のもの）で絞り込め、必要なときに Excel を書き出せる
- 見積作成の画面と Claude のコネクタが、同じ API で「似た過去単価」の候補と按分後の単価を得られる

## Approach

- 受領見積を台帳として兼ねる。依頼なしの受領見積を持てるようにする拡張と、明細行・受領見積への台帳の項目の追加は、データの持ち主である estimate-request の拡張で行う。本 spec はその上に台帳の責務を置く
- 過去カードの取り込みは、管理者の画面からカードの zip（または JSON 群）をまとめて取り込む。コネクタの完成を待たずに移行できるようにする
  - 取り込み時の検査は「読み込めること」と必須の項目（業者・見積日・行）に絞り、細かい不整合では止めない
  - 不整合や参考の印は「参考」として残す
  - 業者名は文字で持ち、登録済みの取引先と一致すれば紐付ける
- 似た単価の検索は PostgreSQL の pg_trgm を使う
  - 名称・規格の文字の近さと単位の一致で候補を絞る
  - 工種・改修／新営・地域・見積日の新しさで並べる
  - 参考の印の候補は【参考】として区別する
  - 本番 DB の lc_ctype が C でないことを着手前に確かめる。1〜2 文字の語は精度が低いため、正規化や部分一致との併用を設計で決める
- 按分の計算
  - 按分率 ＝（諸経費＋交通費＋法定福利費＋値引き）÷ 直接工事分の合計。値引きは負の値として入る
  - 産廃は直接工事分として扱い、別途は除く
  - 候補ごとに「単価・諸経費按分・値引き按分・反映する単価」の内訳を返す
  - 単価が空で金額だけの行は「金額 ÷ 数量」、一式だけの行は換算した単価を使う
  - 反映する単価がマイナスになる候補は反映できない印を返す
  - 端数は見積作成の丸め規則（estimate-creation 要件22）に合わせる
- 時期による単価の補正はしない。見積日を必ず返す

## Scope

- **In**:
  - 台帳の管理者画面（一覧・検索・絞り込み・明細の閲覧と修正・要確認の絞り込み・読取の確認の更新）
  - 過去の見積カードの一括取り込み（全件。原本のパスは文字で保持）
  - 台帳の Excel 書き出し（管理者だけ。出力の監査記録の対象）
  - 似た過去単価の検索と按分計算の API（見積作成の画面とコネクタが使う）
  - 台帳の管理の権限と、似た単価の参照の権限（見積の編集者）
  - 候補の案件名・原本のパスの表示制御（閲覧範囲内の案件と、案件の無い過去カードだけに表示。範囲外は「他案件」）
- **Out**:
  - 受領見積のモデルと登録画面の拡張（estimate-request の拡張が持つ）
  - 見積作成の画面での候補の表示と実行金額への反映（estimate-creation の拡張が持つ）
  - コネクタの操作（claude-connector が持つ）
  - 原本の PDF の移行・保管
  - 時期による単価の補正、意味の近さによる検索（埋め込み等。後で必要になれば検討）
  - 共通スクリプト（daicho）とスキルの改修（本リポジトリの外）

## Boundary Candidates

- 台帳の取り込み（カードの形式の読み取り、業者名と取引先の照合、参考の印の付与）
- 台帳の管理（管理者画面、修正、要確認、Excel 書き出し）
- 類似単価の検索（pg_trgm の索引、並べ方、閲覧範囲による表示制御）
- 按分計算（区分ごとの合計、按分率、反映する単価の内訳、丸め）

## Out of Boundary

- 受領見積の登録・OCR・NET 金額の流れ（estimate-request）
- 見積の明細の編集と保存（estimate-creation）
- 認証・認可・閲覧範囲・出力記録の仕組みそのもの（user-authentication）

## Upstream / Downstream

- **Upstream**:
  - estimate-request の拡張（依頼なしの受領見積、明細行と受領見積への台帳の項目）
  - user-authentication（RBAC、要件39 の閲覧範囲、要件40 の出力記録）
  - trading-partner-management（業者名と取引先の照合）
- **Downstream**:
  - estimate-creation の拡張（似た単価のパネルと実行金額への反映）
  - claude-connector（台帳の検索・登録の操作）
  - ローカルのスキル（vendor-quote-ledger・bim-estimate）の切り替え

## Existing Spec Touchpoints

- **Extends**: なし（新規 spec）。前提として estimate-request の拡張が先に入る
- **Adjacent**:
  - estimate-request — 受領見積のモデルと登録の画面の持ち主。台帳は読み取りと台帳の項目の更新だけを行い、登録の流れは変えない
  - estimate-creation — 要件4.5（転記元は見積依頼で登録した受領見積に限る）と要件22（丸め）。検索 API の利用者
  - execution-budget-management — 実行予算と単価の語が近いが、責務は重ならない

## Constraints

- IPA 注意喚起の是正と同じブランチで進める。是正計画の §4 の守りに従い、estimate-request の拡張とその IPA の是正（5.5）を同じ回にまとめて閉じた後に着手する
- 台帳と業者の見積は社外秘。台帳全体の閲覧と書き出しはシステム管理者だけとし、書き出しは出力の監査記録に残す
- 技術スタックは既存のまま（Express 5、Prisma 7、PostgreSQL、React 19）。pg_trgm は migration で有効化し、索引はスキーマに書く（ずれの検出を避けるため）
- 生成物は日本語（spec.json.language=ja）
- 要件は E2E で画面の結線まで確かめて完了とする
