# 開発規律（プロジェクト全域）

本書は `.kiro/steering/` に置かれ、**毎セッションの読み込み対象**である。特定のスペックの
境界に属さず、実装者・レビュアー・デバッガのいずれにも等しく掛かる作法だけを載せる。

## 実装者へ常に渡す固定集合（タスク 115.291 の宣言）

**統括役（`kiro-impl` を回す親）は、タスクごとの steering の選択を始める前に本節を読み、
ここに挙がるものを境界によらず無条件に実装者へ渡す。** 「このタスクの境界に直接関わるか」
で絞ってはならない。ここに挙がるのは横断的な記録作法であり、**境界で絞ると構造的に落ちる**
——タスク 115.243 が同じ論点で三度差し戻されたのがその実例である。

### 何を渡すか

1. **本書の全文**（`.kiro/steering/development-discipline.md`）。抜粋ではなく全文を渡す。
2. **記録作法の Implementation Notes**。所在は `.kiro/specs/site-survey/tasks.md` であり、
   範囲は次のコマンドで宣言する。**日本語で範囲を宣言してはならない**——下の
   「「掃き終えた」を未検証の前提で支えない」の第 2 層と同じ理由である。

   実装者へ渡す本文はこれで取り出す。

   ```
   grep -E '^- \*\*[^*]*(記録|逐語|引用|開示|併記|注記|明記|書くこと|書かないこと|書き分け)[^*]*\*\*:' .kiro/specs/site-survey/tasks.md
   ```

   見出しだけを一覧するにはこれを使う。

   ```
   sed -nE 's/^- \*\*([^*]+)\*\*:.*/\1/p' .kiro/specs/site-survey/tasks.md | grep -E '記録|逐語|引用|開示|併記|注記|明記|書くこと|書かないこと|書き分け'
   ```

いずれも 83 件を返す（コミット `a1f52968`、2026-09-05 にリポジトリルートで実測。本節の以降の
実測はすべて同日・同コミットの作業ツリーで行った）。母集団は同ファイルの箇条書き 954 件
（`grep -cE '^- \*\*' .kiro/specs/site-survey/tasks.md` の出力）で、うち見出しを取り出せる形は
943 件である（上の見出し列挙から絞り込みを外した数）。**取り出せない 11 件も後任が再現できる
形で挙げる**——
`grep -nE '^- \*\*' .kiro/specs/site-survey/tasks.md | grep -vE '^[0-9]+:- \*\*[^*]+\*\*:'`
が全件を印字する。一件ずつ読むと「要処置」の欠陥報告 9 件・未実装の残存を述べる項 1 件・
恒真の三形の項 1 件であり、記録作法の項は含まれない（内訳は上の出力へ `grep -cF '【要処置'`
を重ねて 9 を得た残り 2 件を読んだもの）。

選別を綴りだけで置いたのは、これが**書き手の自己分類に依存しない**ためである。「実測」
「件数」「報告」まで広げると 143 件へ膨らみ、記録作法でない項が大量に入る。**広い側へ寄せた
誤りは渡す量が増えるだけだが、狭い側へ寄せた誤りは学びを落とす。迷ったら広い側へ倒すこと。**

**代償は渡す量が 32 件増えることである**（51 件 → 83 件）。増えた 32 件のうち、狭義の記録作法

- `「注記が言う未実装」を鵜呑みにしないこと`（読み方の作法）

### なぜ配布物側（`.claude/` 配下）へ宣言を置かないか

この宣言を cc-sdd の配布物へ書き込むことはできない。理由は本書が既に述べている——下の
「なぜ本書に置くか（`.claude/skills/` へ書かない理由）」の節を見よ。同節の趣旨は、配布物は

**したがって宣言の置き場所は本書しかなく、宣言を読んで渡すのは親の仕事になる。**

### どこまで機械が見ているか（三層）

**本節の宣言を守らせる関門は無い。**

1. **機械保証**: 無い。本節は宣言であって関門ではなく、タスク 115.291 は関門を新設して
   いない。
2. **人手走査**: 押下前の関門に載る検査を
   `grep -oE 'npm run check:[a-z0-9-]+' .husky/scripts/pre-push.sh | sort -u` で列挙すると

3. **未走査の残余**: 上の 14 本の外（外した三本、統合の工程、他パッケージの検証、

**この宣言が守られるかは親の振る舞いに依存する。** 親が本節を読まずに steering を選んでも、
実装者が固定集合を渡されないまま作業しても、押下前の関門は赤くならない。**渡されなかった
という事実は、記録にも機械の出力にも残らない。**

## 反実仮想を書く前に変異を実行する

**「この変異を当てれば赤くなる／緑のままである」という記述を、変異を実行せずに書いてはならない。**

反実仮想とは、コードへ仮定の改変（変異）を加えたときに検証・検査がどう転ぶかを述べる記述である。
これは後任が「その検証は本当に効いているのか」を判断する根拠になるため、誤っていると誤診を招く。

### なぜ在るか（三度の実例。タスク 115.210 が起票された経緯）

- **タスク 115.168（否定の側）**: 「同一機能の一覧が段落をまたぐ形が実データに 4 件あり、
  区間の判定を狭めると被覆を過小に見せる」と**測らずに断言**し、その線を自己検査で固定した。
  実測すると失われるのは 2 件だけで、両方とも偽の被覆主張だった。
- **タスク 115.170（レビュアーの側）**: 「ツールバーの `overflowX` を外せば赤になる」と
  レビューが例示したが、実測では緑のままだった。封じ込めていたのは祖先の `overflow: hidden`
  だった。
- **タスク 115.171（実装者の肯定の側）**: 「撤去した恒偽の分岐が生きていれば等倍リサイズが
  入る」とコメントに書いたが、**逐語復元は一度も実行していなかった**。実測すると 48/48 緑で、
  恒偽の分岐は復活させても本体に入らなかった。

いずれも「この変異ならこうなるはずだ」を実行せずに書いたことに起因する。**記述が検査や
コメントに固定されると、後任が誤診する。**

### 守るべきこと

1. **実行してから書く。** 変異を当て、対象の検証・検査を走らせ、出力を読む。
2. **当てた変異を名指しする。** どのファイルのどの記述をどう変えたかを、後任が再現できる
   粒度で書く（「`TYPE_EQUALITY_MATCHERS` から `toStrictEqual` を外す」）。
3. **出力を引く。** 落ちた件数・全体の件数・比・実測した日付のいずれかを必ず書く
   （「自己検査 182 件のうち 1 件が落ちる。2026-08-31 に実測」）。「実測した」だけでは足りない。
4. **元へ戻す。** 変異は必ず復元する。復元は退避した控えからの書き戻しで行い、
   版管理の破壊的な操作（作業ツリー全体の巻き戻し）は使わない。
5. **実行できないなら書かない。** 反実仮想を落とすか、実行できる形へ言い換える。

この作法は**コメント・アサーションの説明・レビューの指摘・状況報告のすべて**に掛かる。

### どこまで機械が見ているか

コードの注釈（`.ts` / `.tsx`）については機械の関門がある。

- **検査**: `npm run check:cf-evidence`（自己検査は `npm run check:cf-evidence:selftest`）。
  押下前の関門と統合の両方に算入されている。記録に書いた件数を数え直すには
  `npm run check:cf-evidence:survey` を使う（追試の手段を成果物に残すため）。
- **判定**: 注釈の塊を文へ割り、コード上の名前の名指し・変異の語・検査の判定の語を
  同じ文が揃えるものを「反実仮想」とし、同じ塊に「実行を述べる語 + 数字」が無ければ失格。
- **機械が届かない範囲**: レビューの発言、設計文書、タスク一覧、状況報告。三度の実例のうち
  機械が届くのはタスク 115.171 の型（コメント）だけである。**残りは本書が拘束する。**
- **保証しないこと**: 検査が見るのは文面であって、変異が本当に実行されたかではない。
  引用を書いておきながら実行していない記述は機械では捕まらない。**引用の中身の妥当性は
  レビューが読む。**

### 提出物に必ず書くこと

機械が届かない範囲は、提出物の書式で拘束する。

**実装者・デバッガ**は、反実仮想をどこか（コメント・アサーションの説明・状況報告）へ一つでも
書いたなら、状況報告に**実行した変異とその実出力**を列挙しなければならない。一つも書いて
いないなら「該当なし」と明記する。列挙の粒度は後任が再現できる形とする。

> 例: 「`TYPE_EQUALITY_MATCHERS` から `toStrictEqual` を外す →
> `npm run check:e2e-guards:selftest` が 182 件中 1 件落ちる（2026-08-31 実測）」

**レビュアー**は次の四つを行う。

1. `npm run check:cf-evidence` を実行する（機械が見るのはコード注釈の `.ts` / `.tsx` のみ）。
2. 差分と実装者の報告を読み、**実行した変異を名指しせず出力も引かない反実仮想**があれば
   差し戻す。
3. **この作法はレビュアー自身にも掛かる。** 「この規則を外せば赤くなる」という指摘を、
   変異を実行せずに書いてはならない。タスク 115.170 はレビュアー側でこれを破った実例である。
4. **記録が引く逐語を `grep -F` で取り直す。** 実装者の報告と差分のうち逆引用符が掛かった
   文字列について、出典参照と取り出しコマンドが同じ場所に在るかを見て、逐語一致で実際に
   取れることを確かめる。取れないものは差し戻す。求める形は「記録が引く逐語は提出時に
   取り直す」節に置いた。**タスク 115.243 は三度ここで差し戻された。**

変異の復元は退避した控えからの書き戻しで行う。版管理の破壊的な操作で戻してはならない。

### なぜ本書に置くか（`.claude/skills/` へ書かない理由）

この作法を cc-sdd の配布物（`.claude/skills/`、`.claude/commands/`、`.claude/agents/`）へ

`.kiro/settings/`（templates / rules）であり、実装・レビュー工程が読むのは前者である。

## 「掃き終えた」を未検証の前提で支えない（タスク 115.149 の教訓）

全称否定（「もう残っていない」）を書くときは、次の三層に分けて書く。

1. 機械保証（コマンドで再現できる範囲）
2. 人手走査（走査範囲を**コマンドで**宣言し、目視した件数を併記する。日本語で範囲を
   宣言してはならない——同じ記述から出発した二者の走査範囲が 2 倍ずれた実例がある）
3. 未走査の残余（反例を示せば偽になる命題として挙げる）

結論は「残存 0」ではなく「(1) と (2) の範囲で 0 件であり、範囲外は保証しない」と書く。

## 記録が引く件数は提出時に測り直す（タスク 115.189 の教訓）

記録を書き足す行為そのものが件数を動かすことがある。実例として、撤去の記録を設計文書へ
書き足したこと自体が `npm run check:design-path-refs` の免除件数を 107 件から 119 件へ
動かした（タスク 115.204 の実測。増分 47 件のうち 12 件は記録の文章自身が増やした分だった。
本書の執筆時点——タスク 115.210、コミット `9b8b151`、2026-08-31——でも同検査は 119 件を
報告していた。**タスク 115.235 の提出時点の再実測は 123 件である**——コミット `46f1138`、
2026-09-02 にリポジトリルートで実測。同検査が走査する 13 件は `.kiro/specs/*/design.md` で
あり、本書はその中に入らない——走査対象は同検査の出力が印字する。本タスクの追記の前後で
測ったところ、いずれも 123 件であった）。
**件数を引く記述は、提出の直前に測り直すこと。** 併せて、**名乗る母集団と追試の手順**
（どのコマンドを、どの起点で走らせるか）を数値と同じ場所に書くこと。起動位置によって
基準が変わる検査があるためである。

**現況を名乗る値には、実測日だけでなくコミットのハッシュを添えること。** 同じ日に複数の
タスクが着地した実例が本リポジトリにあり、その日については日付だけで版を一つに絞れない
（タスク 115.212 が設計文書へ定めた作法を、タスク 115.235 が本書へも適用した）。
**上の免除件数がその実例である**——執筆時点のコミット `9b8b151` では 119 件、同じ
2026-08-31 に着地したコミット `b999b2d`（タスク 115.212）では 123 件であり、日付だけを
手掛かりに 2026-08-31 の版を選ぶと、選んだ版によって値が二つに分かれる。両コミットの
作業ツリーで `npx tsx scripts/check-design-path-references.ts` を走らせて確かめた
（2026-09-02 に実測）。**過去の観測を経緯として残すときは、当時の値を残したうえで現況の
再実測を同じ場所へ並べる。**

本書の新設時にも同じことが起きた。タスク 115.210 は `npm run check:cf-evidence` の説明へ
実測値を書き足したが、**書き足した文章自身が母集団を三度動かした**——説明の書き足しで
32 件から 33 件へ、過検出の中身を引いたことで 33 件から 34 件へ、実行した変異と出力を
書き足したことで 34 件から 35 件へ（いずれも 2026-08-31 に実測。この 35 件は
`npm run check:cf-evidence:survey` が「名指し＋変異＋判定」の三条件で挙げる文の数であり、
執筆時点のコミット `9b8b151` では 35 文 / 9 ファイルであった。**タスク 115.235 の提出時点の
再実測は 62 文 / 18 ファイルである**——コミット `46f1138`、2026-09-02 にリポジトリルートで
実測）。**規律に従って実測を書き足す行為そのものが、次に測るべき数字を動かす。** 数字は
文章を書き終えた後に測り直して入れること。

**上の四つの数値（免除件数の再実測と、その追記前後の再測、`check:cf-evidence` の母集団の
文とファイルの数）は機械が見ている。** タスク 115.276 が
`scripts/design-measurements.json` へ宣言を置き、`npm run check:design-measurement-freshness`
の所管に本書を加えた。宣言は**記録が書き込まれた版を名指す形**で固定してある
（タスク 115.273 の作法）——これらは過去の版についての記録であって現況の主張ではないため、
作業ツリーを読む形で宣言すると記録そのものが偽になる（実際 `check:cf-evidence` の母集団は
上の 62 文 / 18 ファイルに対し現況が別の値である。現況は
`npm run check:cf-evidence:survey` の要約行が印字する）。**上の数値を測り直して書き換える
ときは、新しい版を名指す宣言を同時に足すこと。** 足さずに書き換えると同検査が赤くなる。
本書の実測値のうち、行の中に数値と実測日が同居する形は
`npm run check:steering-dir-counts` の所管だが、**本書は同検査の走査対象ではない**——同検査は
行を単位に見るため、複数行にまたがる本書の散文では規約 (a) を満たす記述まで告発される
（同検査の冒頭注釈に一文書ごとの実測がある）。

**「一件ずつ読んだ」と書くなら、同じ列挙を後任が再現できる形にすること。** 件数だけを出す
出口では読み直しを追試できず、網羅の主張が静かにずれる。タスク 115.210 は実際にここで
差し戻された（33 文のうち過検出を「1 文」と書いていたが、実測では 2 文だった）。是正として
`npm run check:cf-evidence:list` が照合対象の全文を印字する。

**「この条件があるから外れている」も、外してみるまで書かないこと。** 同じタスクは二度目も
ここで差し戻された。過検出の説明文が網に掛からない理由を「名指しを持たないため」と書いた
が、実測すると名指しを足しても件数は動かず、拘束していたのは変異の語と判定の語の不在で
あった。**除外の理由を述べる記述も反実仮想である**——115.170（封じ込め要因を取り違えた例）
と同型であり、当てるべき変異は「その条件だけを足す／外す」である。

## 記録が引く逐語は提出時に取り直す（タスク 115.243 の教訓）

前節は**件数**について述べたが、同じことが**引用した文言**についても成り立つ。記録を書く
時点では手元に差分があり、被置換テキストは「思い出せる」。思い出して書いた要約へ、逐語で
あることを意味する記号（逆引用符）を掛けると、**リポジトリのどこにも無い文字列が逐語として
記録に残る。**

### なぜ在るか（同じ記録の中で、正しい引用と実在しない引用に分かれた）

タスク 115.243 は関門の不在を実証する変異を二つ記録した。**変異 (a) の引用は逐語で正しく、
変異 (b) の引用はリポジトリに実在しなかった。** 差は注意力ではない。

- **(a) の旧形は自己完結した 1 行だった。** 逐語は `npm --prefix backend run test        # 全テスト実行`、出典参照は `f8b97dd:.kiro/steering/tech.md`、取り出しは `git show f8b97dd:.kiro/steering/tech.md | grep -cF 'npm --prefix backend run test        # 全テスト実行'` で、出力は 2 である（コミット `df5dd567`、2026-09-05 にリポジトリルートで実測）。**1 行に収まるものは、そのままコピーできた。**
- **(b) の旧形は折り返した 2 行だった。** 出典参照は `f8b97dd:.kiro/steering/structure.md`、
  取り出しは `git show f8b97dd:.kiro/steering/structure.md | sed -n '1622,1623p'` である
  （出力は 2 行。版を固定しているため行番号は動かない。同日に実測）。**本節はこの 2 行を
  逆引用符で引かない**——1 行に収まらないものを 1 行へ縮めた時点で、それは逐語ではなく
  要約だからである。115.243 の記録はここで縮め、縮めた要約へ逆引用符を掛けた。要約の語彙は
  差分の `+` 側（置換後の新しい記述）から混入しており、
  `git grep -c '全件' f8b97dd -- .kiro/steering/structure.md` は当たりを一つも返さない
  （出力は空、終了コードは 1。同日に実測）。

**分けていたのは「1 行に収まるか（＝そのままコピーできるか）」という機械的な条件である。**
注意深さを求めても塞がらないため、作法で塞ぐ。

**実在しなかった逐語そのものは、ここでは引けない。** 差し戻しは提出前の作業ツリーで起き、
版管理へ入ったのは是正後の形だけである。**取り出せないものを引用しないことが本節の要求で
あるから、本節も引用しない**——経緯はタスク一覧の 115.288 と 115.289 の項が述べる。

### 守るべきこと

1. **逆引用符は逐語にのみ掛ける。** 逆引用符は「この綴りのままリポジトリのどこかに在る」と
   いう主張である。**要約に掛けてはならない。** 要約であることを示したいなら鉤括弧で囲むか、
   「〜の趣旨の記述」と書く。
2. **逐語には出典参照と取り出しコマンドを同じ場所へ置く。** 出典参照は `<commit>:<path>` の
   形とし、版を固定する（作業ツリーを指すと記録が後から偽になる。タスク 115.273 の作法）。
   取り出しコマンドは `grep -F` のように**逐語一致で引く**形にする。正規表現で引く形は、
   書いた綴りと当たった綴りが違っても当たりうるため根拠にならない。複数行を指すときは、
   版を固定したうえでの行範囲の切り出し（上の (b)）でよい——版が固定されていれば行番号は
   動かない。
3. **提出の直前にそのコマンドを実行する。** 実行して実際に取れることを確かめてから提出する。
   前節が件数について求めることと同じ理由である——**記録を書く行為そのものが記録の前提を
   動かすため、書き終えた後に取り直す。**
4. **1 行に収まらないものは逆引用符で引かない。** 折り返した複数行・字下げを含む塊・長い
   段落は、逐語のまま複数行として貼るか、取り出しコマンドだけを書いて本文は要約と明示する。
   115.243 が作った実在しない逐語は、上の (b) と同じくこの形であった。

### どこまで機械が見ているか

**記録が引く逐語の実在を見る関門は、下の変異が覆う範囲には無い。** 三層に分けて書く。

1. **機械保証**: 無い。タスク 115.288 が新設した `npm run check:steering-command-annotations`
   が見るのは steering の註と実挙動の一致であり、記録が引いた文字列が出典に在るかは見ない。
2. **人手走査**: 押下前の関門に載る検査を
   `grep -oE 'npm run check:[a-z0-9-]+' .husky/scripts/pre-push.sh | sort -u` で列挙すると
   17 本が挙がる（2026-09-05 に実測）。うち下の変異を当てたのは 14 本で、外したのは
   `check:req-coverage`（本タスクと無関係に既に赤）と、E2E の書き方だけを読む
   `check:e2e-guards` / `check:e2e-selfjudge` の三本である。**14 本とも緑のままである。**
3. **未走査の残余**: 上の 14 本の外（外した三本、統合の工程、他パッケージの検証、
   レビューの読み）は保証しない。反例が在れば本記述は偽になる。

タスク一覧の記録を機械へ載せるかは**タスク 115.290 が判断し、関門を新設しないと決めた。**
起票が挙げた宣言方式は版を固定した出典参照を伴う逐語にしか置けないが、タスク一覧には
その形の肯定の引用が一つも無く、据えても守る対象が無いためである。素朴に「逆引用符の
中身は実在すること」を全件へ課す形も、逐語でない綴り（行番号つきのパス・実行すべき

**この不在は変異で確かめてある。** 本書へ、リポジトリのどこにも無い合成の文字列を逐語として
