# ブラウザ動作確認による要件検証ガイドライン

現在のブランチで変更されたすべての要件を、ローカル開発環境上でブラウザを使い手動検証する。

## 1. 検証対象の特定

### 1.1 変更されたrequirements.mdの検出

以下のコマンドで、現在のブランチで変更された要件ファイルを特定する。

```bash
git diff develop --name-only -- '.kiro/specs/*/requirements.md'
```

変更されたrequirements.mdが存在しない場合、その旨を報告して終了する。

### 1.2 変更された要件の抽出

各requirements.mdについて、`git diff develop` の差分から追加・変更されたAcceptance Criteriaを特定する。取消線（`~~`）で無効化された要件は検証対象から除外する。

### 1.3 検証計画の提示

検証開始前に、以下の情報をユーザーに提示する。

- 対象のrequirements.mdファイル一覧
- 各ファイルから抽出した検証対象の要件（Requirement番号とAcceptance Criteria）
- 検証の順序

## 2. ローカル開発環境の起動

`local-dev-env`スキルのガイドラインに従い、ローカル開発環境を起動する。

- README.mdから正しい起動コマンドを確認する
- 既に起動済みの場合は二重起動しない
- アクセス先URLをREADME.mdから正確に取得する

## 3. ブラウザによる要件検証

### 3.1 検証手順

検証対象の各Acceptance Criteriaについて以下を実行する。

1. Playwright MCPを使用してブラウザを起動する
2. 該当機能の画面に遷移する
3. Acceptance Criteriaに記述された条件・操作を実際に行う
4. 期待される結果が得られるかを確認する

### 3.2 検証の記録

各Acceptance Criteriaの検証結果を以下の形式で記録する。

- **対象**: Requirement番号 / AC番号
- **操作内容**: 実際に行った操作
- **期待結果**: ACに記述された期待動作
- **実際の結果**: 観測された動作
- **判定**: PASS / FAIL

### 3.3 FAIL時の対応

検証がFAILとなった場合、即座に修正は行わず、すべての検証を完了してから結果をまとめて報告する。修正の要否と方針はユーザーの判断を仰ぐ。

## 4. 検証結果の報告

すべての検証完了後、以下を含むサマリーを報告する。

- 検証対象の総数
- PASS / FAIL の件数
- FAILとなった要件の詳細（Requirement番号、AC番号、観測された問題）
- 必要に応じたスクリーンショット
