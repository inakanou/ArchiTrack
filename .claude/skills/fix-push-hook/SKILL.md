# git pushフック失敗対応ガイドライン

## 1. ログ調査手順（コンテキスト節約）

ログファイル `.logs/pre-push-latest.log` を以下の手順で調査する。ログ全体を一括で読み込んではならない。

1. **末尾から読む**: ログの末尾（最後の50〜100行程度）を読み、失敗要因のサマリーやエラーメッセージを特定する
2. **失敗箇所を遡る**: 特定した失敗要因をもとに、関連するキーワードでログ内を検索し、具体的な失敗箇所を絞り込む
3. **必要最小限の読み取り**: 失敗箇所の前後のみを読み取り、原因を確定する

### 禁止事項

- ログファイル全体を一括で読み込むこと
- 失敗要因が不明なままログを先頭から順に読むこと

## 2. 修正対応

失敗原因を特定したら、該当箇所を修正する。

## 3. 再pushと作業完了の定義

修正後は、git push をやり直してよい（ユーザーがあらかじめ許可している）。

- **再pushの上限**: やり直しは2回まで（最初のpushと合わせて3回）。3回目も通らなければ、原因と修正内容を報告して止める
- **再pushせずに報告して止める場合**:
  - 修正後も同じ原因で失敗した
  - 失敗の原因を特定できない
  - 修正に要件・設計の判断が必要である（ユーザーの決定を待つ）
- **メモリ不足による停止**（Claude Code がメモリ不足で背景のコマンドを止めた場合）: テストの失敗ではない。空きメモリと `/tmp` の使用量を確かめ、残った試験用のコンテナを止めてから、1回だけやり直す。再び止められたら報告して止める
- 各回の失敗原因・修正内容・結果は、最後にまとめてユーザーへ報告する

### 禁止事項（再pushでも変わらない）

- `--no-verify` などで検査を飛ばすこと
- テストの主張を弱める、前提条件でテストを自動的に無効化するなど、検査を通すためだけの修正（AI運用7原則の第3原則）
